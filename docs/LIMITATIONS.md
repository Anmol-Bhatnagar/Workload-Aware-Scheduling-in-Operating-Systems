# Project Limitations & Threats to Validity

Honest disclosure of scientific boundaries, assumptions, and hardware constraints.

---

## 1. Scope & System Boundaries

1. **Simulation vs. Live Kernel Scheduling:**
   The CPU scheduling experiment is conducted within a controlled, discrete-event Python simulation environment. It does **not** modify or replace the live Linux kernel CPU scheduler (such as EEVDF), does not execute kernel-level thread dispatches, and does not operate at microsecond interrupt hardware scales.
2. **Textbook Baselines:**
   The Shortest Job First (SJF) implementation is an offline, clairvoyant textbook baseline that accesses known CPU burst durations generated by the synthetic profile. A production OS does not possess future burst knowledge and must rely on exponential smoothing or heuristic estimators.
3. **Single CPU Assumption:**
   The simulator models a single uniprocessor CPU core. Multiprocessor SMP phenomena (cache affinity, NUMA balancing, work-stealing, inter-processor interrupts) are outside the model scope.
4. **Synthetic Workloads:**
   Workload profiles are parameterized synthetic models (CPU-bound, I/O-bound, interactive, mixed, bursty arrivals) designed to test classical trade-offs. They do not represent production data-center or enterprise server telemetry.

---

## 2. Machine Learning Boundaries

1. **Generator-Bound Decision Trees:**
   The Decision Tree recommender is trained exclusively on synthetic scenarios generated by `WorkloadGenerator`. Its high accuracy reflects the statistical boundaries of these generated distributions; its performance on arbitrary real-world workloads would require trace calibration.
2. **Composite Objective Weighting:**
   The composite cost function is a research instrument weighting response time (30%), waiting time (25%), turnaround time (20%), context switches (15%), and CPU utilisation (10%). Changing these weights alters the optimal policy labels, as documented in the sensitivity analysis.
3. **No Direct Kernel Control:**
   The model produces a scenario-level recommendation (e.g. recommending Round Robin with $q=2$ for interactive workloads). It does not act as an in-kernel dispatch function for individual process ticks.

---

## 3. Storage I/O Hardware & Environment Constraints

1. **Host-Specific Measurements:**
   Storage benchmarks using `fio` measure performance strictly on the specific host hardware, storage controller, and filesystem tested. Findings from NVMe SSDs cannot be generalized to mechanical rotational disks (HDDs), network-attached storage (NFS), or cloud virtual disks.
2. **Exposed Scheduler Constraints:**
   Modern NVMe solid-state storage often exposes only the `none` and `mq-deadline` schedulers in Linux kernels. Schedulers like `bfq` may be disabled or uncompiled on modern distros.
3. **Virtualization Caveats (WSL / Containers):**
   When running inside WSL or virtualization, block I/O schedulers may be virtualized or unswitchable. As mandated by the research protocol, under such conditions only the safe, exposed configuration is tested, and the absence of switchable policies is reported honestly.
4. **Target Safety:**
   All benchmarks are strictly confined to disposable scratch files (`data/scratch/fio_test.dat`). Raw block device writes are permanently prohibited to prevent storage corruption.
